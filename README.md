# Connected Animes — アニメのつながりを描く

1本のアニメを起点に、近い作品の地図を描くビューア。論文の関連を可視化する [Connected Papers](https://www.connectedpapers.com/) のアニメ版として作りました。

依存ゼロの静的サイト（`index.html` 1ファイル）です。ビルド不要、APIキー不要、サーバー不要。

---

## なぜ作ったか — 設計に至るまで

### 出発点

「この作品が好きなら次はどれか」を、リスト形式のレコメンドではなく**地図として一望したい**というのが動機でした。Connected Papers が論文で実現していることを、アニメでやりたい。

Connected Papers の肝は、引用関係を類似度に変換して力学配置している点にあります。したがって最初に決めるべきは「**アニメにおいて何を引用の代わりに置くか**」でした。

### 候補1: 視聴者の共起 — 検討したが採用せず

「同じ人が両方リストに入れているか」を数えるやり方です。論文の bibliographic coupling とほぼ同じ数学で、Connected Papers らしい「意外だが納得できる」接続が出やすい。データは Kaggle の MyAnimeList データセット（32万ユーザー・1億行規模）を使えば、収集の手間もかかりません。

**採用しなかった理由は、日本人ユーザーがほぼ含まれていないことです。**

MyAnimeList は英語圏のサービスで、日本のアニメファンはまず使いません。その結果:

- 海外配信された作品に強く偏る（未配信の深夜アニメが薄い）
- 少年漫画原作・長期シリーズが過大評価される
- 日常系、アイドル物など、国内で評価される作品が過小評価される

日本語話者に向けて作る以上、このズレは無視できないと判断しました。日本側の代替として Annict の API も検討しましたが、個人運営のサービスで規模がMALと桁違いのため、共起を成立させる密度には届きません。

さらに共起には**コールドスタート**の問題があります。放送直後の数週間は登録者が少なく、しかも初動で飛びつく層に偏るためシグナルが歪む。「最新作を必ず載せる」という要件とは相性が悪い。

### 候補2: メタデータ — こちらを採用

タグ・ジャンル・スタッフ・制作会社の重なりから類似度を出す方式です。

決め手は、**メタデータには国籍バイアスがない**という切り分けでした。監督が誰か、どの会社が作ったか、どんなタグが付くかは客観的な事実なので、AniList のような海外データベースから取っても日本人向けとして問題ありません。文化差が出るのは「誰が何を観たか」の部分だけです。

この方式なら:

- 海外ユーザーの嗜好が一切入らない
- 放送開始と同時に地図に載る（メタデータは放送前から存在する）
- ブラウザから直接APIを叩けるので、サーバーもデータベースも要らない

### 重みの調整

当初は「タグ余弦 + スタッフ共有 0.15×人数 + 制作会社 0.10」という素朴な加点でしたが、実装後に見直して3点変えています。

**制作会社を軽くした。** 日本のアニメ制作会社の大半は受注生産で、作風の幅が広すぎます。京アニやシャフトのように色が出る会社は、社内に監督とキャラデザが常駐しているから一貫して見えるだけで、スタジオは実質スタッフの代理変数です。スタッフ共有を既に加点しているなら二重計上になる。そこで固定加点をやめ、**その会社の作品群がタグ空間でどれだけ固まっているかを実測して 0.02〜0.10 に可変**としました（`coherence()`）。作風の明確な会社では効き、受注中心の会社ではほぼゼロになります。

**スタッフを役職別にした。** 監督と音楽が同じ重みなのは実態に合いません。監督 0.20 / 原作 0.16 / シリーズ構成・キャラデザ 0.10 / 脚本 0.06 / 音楽 0.04 としています。この過程で、役職判定の正規表現が部分一致だったため `Animation Director`（作画監督）や `Episode Director`（演出）まで監督として拾っていたバグも見つかりました。

**ジャンルを軽くした。** ジャンル（Comedy 等）は判別力が低いのに数が少なく、ベクトルのノルムを占有します。試算すると、タグが6本しかない新作ではジャンルが 56% を占めていました。新作ほどジャンルだけで繋がるという最も避けたい挙動なので、重みを 1.0 から 0.5 に下げています。

### 距離に意味を持たせた

Connected Papers は「似た論文がクラスタとして集まる」と説明しており、**起点からの距離が類似度を表すとは述べていません**。実際、力学配置で「近いほど似ている」と読むのは常に正しいわけではないことが研究でも指摘されています。

本アプリも当初は同じ設計でしたが、実測したところ類似度順位と距離順位の相関は **-0.05**、ほぼ無相関でした。エッジを各ノード上位4本に絞っていたため、起点から直接伸びる線が38本中4本しかなく、残りは他の作品との引き合いだけで位置が決まっていたためです。

そこで、起点との類似度を目標半径に写して動径方向に引き寄せる**同心円配置**を追加しました。角度方向は自由なのでクラスタは残ります。相関は **-0.86** まで改善しています。従来のクラスタ配置にも切り替えられます。

### 同一シリーズの扱い

続編や前日譚は類似度を独占してしまうため地図から外していますが、ここでも2つ問題が出ました。

1つは、共通キャラクタやスピンオフまで「直系」として一覧に出していたこと。これらは**別作品であり推薦として価値がある**ので、除外せず地図に残す設計に改めました。

もう1つは、AniList の relations が**直接の繋がりしか返さない**こと。『化物語』から見て `偽物語 → 猫物語 → 傷物語` のように離れた作品は除外されず地図に残っていました。関係を**最大3ホップまで推移的に辿って**シリーズ全体を集めるようにしています（GraphQL のエイリアスで10件を1リクエストに束ねるため、追加は3リクエスト程度）。

## 仕組み

1. 起点作品のタグ・ジャンル・スタッフ・制作会社・関連作を AniList から取得
2. 上位タグ / 主要スタッフの担当作 / 同じ制作会社の作品を候補として収集（10リクエスト程度）
3. タグ余弦を土台に、役職別スタッフ共有と制作会社の一致を加点してスコアリング
4. 上位38件をノード化し、全ペアの類似度からエッジを構築（各ノード上位4本）
5. 自作の力学シミュレーションで配置し、SVG で描画

### 見方

| 見た目 | 意味 |
|---|---|
| 円の大きさ | AniList の登録者数 |
| 円の色 | 放送年（淡いほど古い） |
| 中心からの距離 | 起点との類似度（同心円配置のとき） |
| 線の太さ | その2作品どうしのタグの近さ |
| 朱色の円 | 起点 |

右上のボタンで、表示スタイル（円を重ねる／重ねない）と配置（同心円／クラスタ）を切り替えられます。

## 公開と更新

GitHub Pages で公開しています。静的ファイル1つなのでビルド設定は不要です。

### 初回設定

1. リポジトリに `index.html` を**直下**に置く（フォルダごと入れると404になる）
2. リポジトリを Public にする
3. Settings → Pages → Source を **Deploy from a branch**、ブランチ **main** / **/(root)** → Save

公開URLは `https://<ユーザー名>.github.io/<リポジトリ名>/` です。反映まで1〜2分かかります。

### 更新

`index.html` を上書きコミットするだけです。**URLは変わりません**ので、共有済みのリンクはそのまま使えます。

```bash
git add index.html
git commit -m "類似度の重みを調整"
git push
```

ブラウザだけで完結させる場合は、リポジトリの `index.html` を開いて鉛筆アイコンから編集するか、Add file → Upload files で同名ファイルを上げ直します。

### ローカルで確認

```bash
python3 -m http.server 5173     # → http://localhost:5173
```

`file://` で直接開くと AniList への通信が CORS で弾かれることがあるため、簡易サーバー経由を推奨します。

## パラメータ

`index.html` 冒頭にまとめてあります。

| 定数 | 既定 | 意味 |
|---|---|---|
| `NODE_LIMIT` | 38 | 起点を除く表示作品数 |
| `EDGE_PER_NODE` | 4 | 1作品あたりの最大接続数。増やすと毛玉になる |
| `EDGE_MIN` | 0.22 | 線を引く最小類似度（引き伸ばし後の尺度） |
| `TAG_MIN_RANK` | 40 | これ未満のランクのタグは無視 |
| `GENRE_W` | 0.5 | ジャンルの重み。上げるとジャンル一致だけで繋がりやすくなる |
| `COS_LO` / `COS_HI` | 0.12 / 0.67 | 生の余弦をこの範囲で 0〜100% に引き伸ばす |
| `STAFF_CAP` | 0.34 | スタッフ加点の上限 |
| `STUDIO_W` | [0.02, 0.10] | 制作会社の加点幅。作風の一貫性で自動可変 |
| `ROLE_W` | 監督0.20 / 原作0.16 / 構成・キャラデザ0.10 / 脚本0.06 / 音楽0.04 | 役職別の重み |
| `FRANCHISE` | SEQUEL / PREQUEL / SIDE_STORY / PARENT / SUMMARY / COMPACT / ALTERNATIVE / CONTAINS | 同一シリーズとみなす関係。ここから外すと地図に載る |
| `FRANCHISE_HOPS` | 3 | 何ホップ先まで同一シリーズとして辿るか |
| `FRANCHISE_MAX` | 70 | 1シリーズから辿る上限 |
| `RADIAL_FORCE` | 0.135 | 同心円へ引き寄せる力の強さ |
| `STYLES` | overlap / separate | 表示スタイル。半径・衝突判定・リンク距離・不透明度・ラベルの詰め方をまとめて持つ |

### 表示スタイル

| | 円の半径 | 重なり | 合成 | ラベル |
|---|---|---|---|---|
| `overlap`（既定） | 9〜78px | 許容（乗算で濃くなる） | multiply | 円からはみ出す・12文字まで |
| `separate` | 15〜51px | なし（必ず離す） | 通常 | 円の内側に収める |

### スコアの実効比率

タグ余弦は実際には 0.15〜0.65 程度しか使われないため、`stretch()` で 0〜1 に引き伸ばしてから加点と合成しています。これをしないと加点が相対的に効きすぎます。結果として概ね **タグ 70% / スタッフ 24% / 制作会社 6%** の配分になります。

## 次に足すなら

- **結果のキャッシュ** — 同じ作品への再アクセスで AniList を叩き直さないよう、localStorage か外部KVに置く
- **日本側の嗜好シグナル** — Annict の GraphQL API から視聴データを取り、ノードの大きさを「日本での人気」に差し替える
- **海外版** — 類似度計算を MyAnimeList の視聴共起に差し替える。UI はそのまま使える
- **共起とのブレンド** — `w = n / (n + k)` でデータ量に応じて自動で重みを移す。新作はメタデータ、蓄積後は共起へ滑らかに移行できる
